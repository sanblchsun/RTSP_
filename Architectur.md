# Архитектура RTSP_ проекта

## Описание пути кадра

### 1. Захват видео на агенте
- Агент использует Windows Graphics Capture (WinRT) через `WinRT-API/capture_wgc.cpp`.
- Инициализация: создаётся D3D11 устройство и `GraphicsCaptureItem` для монитора.
- Захват выполняется методом `WGCCapture::CaptureFrame()`:
  - `TryGetNextFrame()` возвращает новый кадр, если он доступен.
  - Текстура копируется в staging-текстуру для CPU-read.
  - Данные копируются из `D3D11_MAPPED_SUBRESOURCE` в `std::vector<uint8_t> out_bgra`.
- Формат кадра: BGRA, native разрешение монитора.

### 2. Кодирование видео на агенте
- Агент запускается с `kFps = 30`.
- Используется `WinRT-API/encoder_x264.cpp` и libx264 с настройками:
  - preset `ultrafast`, tune `zerolatency`.
  - цветовое пространство `X264_CSP_I420`.
  - `b_intra_refresh = 1`, `i_keyint_max = fps * 2`, `i_keyint_min = fps`, `i_scenecut_threshold = 0`.
  - `i_bframe = 0`, `i_frame_reference = 1`.
  - `rc.i_rc_method = X264_RC_CQP`, `i_qp_constant = 23`.
  - `b_repeat_headers = 1`, `b_annexb = 1`, `b_aud = 0`.
- Вход конвертируется BGRA → I420 вручную в `bgra_to_i420()`.
- Пакеты x264 с NAL-ами получаются в Annex-B формате.
- SPS/PPS извлекаются из заголовков кодировщика и сохраняются для SDP-сигнализации.

### 3. Пакетизация и передача по RTSP/TCP
- H.264 NAL-ы пакетизируются в `rtp/H264RtpPacketizer`.
- Пакетизатор поддерживает:
  - одиночные NAL в один RTP-пакет;
  - фрагментацию крупных NAL в FU-A;
  - управление sequence и RTP timestamp.
- RTP timestamp генерируется как `rtp_ts += 90000 / kFps`.
- Транспорт: RTSP over TCP interleaved.
- Клиент выполняет handshake: `OPTIONS`, `DESCRIBE`, `SETUP` (`interleaved=0-1`), `PLAY`.
- RTP пакеты инкапсулируются как `'$' channel=0 length data`.
- `TCP_NODELAY` включён на клиенте и сервере.

### 4. Приём на сервере
- Сервер (`webrtc_server.py`) запускает RTSP-сервер на TCP-порту 8554.
- `AgentSession.handle()` принимает соединение агента.
- Поток данных разбирается на две части:
  - interleaved RTP-пакеты (`$ ...`) обрабатываются как RTP;
  - RTSP-запросы парсятся строками и отвечаются `OPTIONS`, `DESCRIBE`, `SETUP`, `PLAY`, `TEARDOWN`.
- Флаг `self._play_sent` начинает передачу RTP после `PLAY`.

### 5. Парсинг RTP и восстановление H.264
- `RtpParser.feed_rtp()`:
  - проверяет RTP header, payload type 96;
  - извлекает RTP timestamp;
  - разбирает payload по NAL-типу.
- Поддерживаемые NAL:
  - одиночные NAL (`type <= 23`) отправляются напрямую;
  - FU-A (`type == 28`) собираются в буфер и восстанавливаются в полный NAL;
  - STAP-A (`type == 24`) разбираются на отдельные NAL.
- Если фрагментация заканчивается, итоговый NAL передаётся в `source_track.feed_nal()`.

### 6. Декодирование и подготовка кадров
- `H264StreamTrack` использует `av.CodecContext.create('h264', 'r')`.
- `feed_nal()`:
  - извлекает SPS/PPS для WebRTC SDP;
  - парсит NAL через декодер PyAV;
  - для каждого `frame` задаёт `frame.pts = rtp_timestamp`, `frame.time_base = Fraction(1, 90000)`;
  - кладёт декодированный кадр в `deque(maxlen=10)` и сигналит `asyncio.Event`.
- Если декодирование падает, пишет warning.

### 7. Очередь кадров и плейаут
- Кадры хранятся в `collections.deque(maxlen=10)`.
- `deque(maxlen=10)` автоматически отбрасывает старые кадры, если очередь переполнена.
- Для отправки в браузер `recv()`:
  - ждёт, пока очередь не станет непустой;
  - берёт первый кадр;
  - рассчитывает интервал `pts_delta = (frame.pts - last_pts) / 90000`;
  - если нужно, ждёт `asyncio.sleep(wait)` на основе разницы реального времени и RTP-интервала;
  - обновляет `_last_pts` и `_last_time`.
- Это относительное pacing по RTP timestamp.

### 8. WebRTC и отдача в браузер
- FastAPI `/offer` принимает SDP offer от браузера.
- Создаётся `RTCPeerConnection`, добавляется `relay.subscribe(source_track)`.
- После создания answer SDP, если SPS/PPS извлечены, в `a=fmtp:96` дописывается `sprop-parameter-sets`.
- Браузер получает поток через WebRTC и отображает видео в `<video>`.

## Краткое резюме узких мест и приоритетов для оптимизации

### 1. RTCP / interleaved канал 1
- На сервере interleaved RTCP не обрабатывается.
- Если агент начнёт посылать RTCP или браузер будет ожидать RTCP ACK/PLI, это не поддерживается.
- Приоритет: низкий для solo-видео, но важно учитывать для расширения на двухпотоковые сценарии.

### 2. Обработка потерь / восстановление
- Сервер не проверяет sequence number RTP и не учитывает потерю/дублирование пакетов.
- На TCP это не критично, но при нестабильном канале и переподключениях могут появляться артефакты.
- Приоритет: средний, если появятся ошибки interleaved TCP или частичные фреймы.

### 3. Декодер и очередь
- Используется `deque(maxlen=10)` без явной метрики задержки.
- Если поток задерживается, старые кадры просто отбросятся, что может привести к пропуску и скачкам.
- Приоритет: высокий для стабильности; стоит логировать drop-кадры и возможно адаптировать размер очереди.

### 4. Pacing на сервере
- Текущее `recv()` делает относительный pacing по `pts_delta`, но не синхронизируется с внешним временем.
- Это нормально для solo video, но требует точной RTP timestamp генерации на агенте.
- Приоритет: средний; особо важно убедиться, что timestamp шаг 90000/30 соответствует реальному 30 FPS.

### 5. SPS/PPS и декодирование в браузере
- Сигнализация `sprop-parameter-sets` зависит от того, что SPS/PPS действительно выйдут в входном потоке.
- Если их не будет, браузер может зависнуть до первого IDR.
- Приоритет: высокий; проверять, что SPS/PPS всегда есть в начале и/или передавать их явно при установке соединения.

### 6. Запросы keyframe / PLI
- Механизм `!K` работает как пользовательская логика, но не стандартный RTCP PLI/FIR.
- Это ок, но если браузер требует стандартного RTCP, нужно будет расширить поддержку.
- Приоритет: низкий для текущего решения.

### 7. Многопользовательские подключения
- `source_track` один для всех, `MediaRelay` дублирует поток на нескольких клиентов.
- Если подключится несколько браузеров, декодирование и очередь остаются общими.
- Приоритет: средний, если нужно масштабировать на несколько зрителей.

## Итог
- Весь путь данных корректно реализован для одного видео-потока: WinRT capture → x264 encode → RTP/TCP → серверный H.264 decode → WebRTC.
- Сильный акцент на low-latency и простую относительную синхронизацию через RTP timestamps.
- Главное внимание стоит уделить очереди/дропам, SPS/PPS сигнализации и правильному таймингу RTP timestamp на агенте.
